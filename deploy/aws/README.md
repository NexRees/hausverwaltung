# NexRees on AWS

Terraform for NexRees in AWS Frankfurt (`eu-central-1`). One module, one folder per environment:

| Path | What |
|---|---|
| `modules/stack` | VPC (2 zones), load balancer with TLS, ECS Fargate app, RDS Postgres 16, S3 documents bucket, KMS key, Secrets Manager, GitHub OIDC deploy role |
| `envs/staging` | `staging.nexrees.de`, three staff logins |
| `envs/production` | `app.nexrees.de`: same module, plus Multi-AZ database, 35-day backups, deletion protection |
| `modules/stack/tests` | Offline security checks: `terraform init -backend=false && terraform test` |

## Safe deployment profile

The same module runs staging and production; only the values in `envs/<env>/main.tf` differ,
so whatever works on staging is what production gets. Guard rails:

| Guard | How |
|---|---|
| Frankfurt only | Provider, state bucket and CI all use `eu-central-1`; the module refuses to plan in any other region (test `refuses_any_region_but_frankfurt`). Only AWS's global control plane (IAM roles, GitHub OIDC provider, cost budget) has no region, and it holds no customer data. |
| Right account only | Each env takes `aws_account_id` and sets `allowed_account_ids`: Terraform stops before any change if the logged-in profile is another account. |
| No root, no long-lived keys | People use an IAM Identity Center profile (`aws configure sso --profile nexrees`); GitHub Actions use OIDC roles, no stored AWS keys. |
| Deploys scoped to an environment | Each deploy role trusts only jobs in the GitHub environment of the same name (`environment:staging` / `environment:production`), and may only roll its own ECS service. |
| Same image, proven first | Every commit on `main` builds `sha-<short>` and rolls staging. Production gets an image only via **Promote to production**, which resolves the tag to its digest, checks staging runs exactly that image, waits for approval, then deploys `image@sha256:…`. |
| Automatic rollback | ECS deployment circuit breaker: a release that never gets healthy is rolled back to the previous revision. |
| Separate state | `nexrees-hv/staging.tfstate` and `nexrees-hv/production.tfstate` in a private, versioned bucket. |
| Cost alerts | AWS Budget per env (staging $90, production $150 a month, usage before credits): e-mail at 50 / 80 / 100 % and when the month's forecast passes 100 %. With ~€200 credit, staging alone runs about 2.5 months. |
| Data | Staging only ever gets demo data or anonymised copies of production, never a raw copy. |

### GitHub settings (once)

- Settings → Environments → `staging`: deployment branches = `main` only.
- Settings → Environments → `production`: deployment branches = `main` only, **required
  reviewers** = Abi (and whoever else may release), prevent self-review off for a team of one.
- Settings → Variables: `AWS_STAGING_DEPLOY_ROLE`, later `AWS_PRODUCTION_DEPLOY_ROLE`
  (`terraform output -json stack | jq -r .deploy_role_arn`).

### Releasing

1. Merge to `main` → image `sha-<short>` → staging updates by itself.
2. Check staging.
3. Actions → **Promote to production** → tag `sha-<short>` → approve → production runs the
   same digest. To roll back, promote the previous tag.

## How staging is built

- Load balancer and app tasks in public subnets (the app only accepts traffic from the load
  balancer), database in private subnets without internet. No NAT gateway, which keeps
  staging cheap.
- The app container is the image CI publishes for every commit on `main`
  (`ghcr.io/nexrees/hausverwaltung:sha-<short>`). On start it migrates the database, creates the
  tenant and admin on an empty database (`bootstrap.ts`), then the other staff logins
  (`prisma/nexrees-users.ts`).
- Secrets (`DATABASE_URL`, `AUTH_SECRET`, logins) are generated by Terraform and stored in
  Secrets Manager. They are also in the Terraform state, so the state bucket must stay private.
- No SMTP is configured, so staging never sends mail; outgoing mail stays in the app's outbox.
- Rough cost, my estimate from list prices: about €60 to €80 a month (load balancer, smallest
  RDS, one ARM Fargate task, public IPv4 addresses).

## First deploy (once)

Needs: the NexRees AWS account, AWS CLI profile `nexrees` logged in (`aws configure sso
--profile nexrees`, then `aws sso login --profile nexrees`), Terraform 1.9+, and this
repository on GitHub as `NexRees/hausverwaltung`. Every command below uses that profile:

```sh
export AWS_PROFILE=nexrees
export TF_VAR_aws_account_id=$(aws sts get-caller-identity --query Account --output text)
export TF_VAR_budget_emails='["you@nexrees.de"]'
```

Check that the account ID is the NexRees one before going on.

1. **Image.** In GitHub → Actions, enable workflows for this fork and run **Build and push
   image**. Then GitHub → NexRees → Packages → `hausverwaltung` → Package settings → change
   visibility to **Public** (AGPL code anyway; ECS pulls it without credentials). Note the tag
   `sha-<first 7 of the commit>`.

2. **State bucket** (one per AWS account):

   ```sh
   ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
   BUCKET=nexrees-terraform-state-$ACCOUNT
   aws s3api create-bucket --bucket $BUCKET --region eu-central-1 \
     --create-bucket-configuration LocationConstraint=eu-central-1
   aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled
   aws s3api put-public-access-block --bucket $BUCKET --public-access-block-configuration \
     BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
   ```

3. **Certificate first.** The full apply waits until the certificate is validated, so create
   it alone and add its CNAME at INWX:

   ```sh
   cd deploy/aws/envs/staging
   terraform init -backend-config="bucket=$BUCKET"
   IMAGE=ghcr.io/nexrees/hausverwaltung:sha-1234567   # from step 1
   terraform apply -var image=$IMAGE -target=module.stack.aws_acm_certificate.this
   terraform state show module.stack.aws_acm_certificate.this | grep -A4 domain_validation_options
   ```

   INWX → nexrees.de → DNS: add a **CNAME** with the shown `resource_record_name` (without
   `.nexrees.de.`) and `resource_record_value`. Do not touch MX, SPF, DKIM, DMARC or the
   website records.

4. **Everything else:**

   ```sh
   terraform apply -var image=$IMAGE
   terraform output -json stack | jq '.dns_records_for_inwx, .logins, .deploy_role_arn'
   ```

5. **Hostname.** INWX: CNAME `staging` → the load balancer name from `dns_records_for_inwx`.

6. **CI deploys.** GitHub → Settings → Environments → create `staging`; Settings → Variables →
   `AWS_STAGING_DEPLOY_ROLE` = `deploy_role_arn`. From then on every merge to `main` builds an
   image and rolls staging to it (`.github/workflows/nexrees-deploy-staging.yml`).

7. **Logins.**

   ```sh
   aws secretsmanager get-secret-value --secret-id nexrees-staging/app \
     --query SecretString --output text | jq -r '.NEXREES_USERS | fromjson[] | "\(.email)  \(.password)"'
   ```

   Hand each person their password privately; they can change it in the app.

## Company sign-in (Google Workspace)

Everyone with a `@nexrees.de` Google Workspace account can sign in with "Mit Google anmelden".
The first sign-in creates their user with the role `VERWALTER` (an admin can change it under
Benutzer). Accounts outside nexrees.de, unverified addresses and personal Google accounts are
refused. ADMIN is never given automatically. E-mail and password keep working.

1. Google Cloud Console (signed in as a NexRees Workspace admin) → new project `nexrees-sso`.
2. **Google Auth Platform → Branding**: app name NexRees, support e-mail; **Audience**: user type
   **Internal** (only NexRees Workspace accounts can even reach the consent screen).
3. **Clients → Create client** → Web application, name `NexRees staging`:
   - Authorised JavaScript origin: `https://staging.nexrees.de`
   - Authorised redirect URI: `https://staging.nexrees.de/api/auth/callback/oidc`
4. Apply with the client ID and secret (they go to Secrets Manager, never into git):

   ```sh
   export TF_VAR_google_client_id=...apps.googleusercontent.com
   export TF_VAR_google_client_secret=...
   terraform apply -var image=$IMAGE
   ```

Production gets its own client with `https://app.nexrees.de/...`. To change the default role or
add domains, edit the `sso` block in `envs/staging/main.tf`.
